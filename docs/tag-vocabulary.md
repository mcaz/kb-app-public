# MCPからタグ語彙を確認・更新する

2026-09-08本人指定。数万ノートの運用を想定し、タグの付与・付け替えだけでなく、
語彙の追加・統合・削除もAIが判断する。タグごとの本人確認は必須にしない。
既存語で表せる内容には既存語を優先し、同義語や一時的な細分類の増殖を抑える。
本人の明示的な訂正には従い、運用と語彙表へ反映する。
通常ノートはタグ1〜4個、英小文字・数字・ハイフン、20文字以内とする。
通常のMCP書込みは語彙にないタグを拒否し、`allow_new_tags`も受け付けない。

`tag_vocabulary`自体は語彙を変更する引数を持たないが、通常のMCPと同じDB準備・同期経路を使う。
DBの初期化・自己修復や、有効なバックアップ設定に従うGit同期・未出力更新の書出しを伴い得る。
read面は参照用途の分類であり、呼出し全体の無副作用を意味しない。toolのannotationsもこの
副作用に合わせ、完全な読み取り専用診断とは区別する。

## 正本を指定する

語彙の内容はノートの`## 語彙`節に置き、参照先をworkspace_idと不変のnote_uidで固定する。
題名検索は未指定時の候補発見にだけ使う。読取・候補1件だけを理由に自動指定しない。

1. `tag_vocabulary`を呼び、`workspace_id`、`source_status`、`source`、`candidates`を確認する。
2. 未指定なら、候補の`note_id`を`get`して運用と本文を確認する。候補が複数あっても検索順位で
   決めず、AIが用途に合うノートを選ぶ。候補がなければ通常の起票で語彙ノートを作る。
3. write面の`set_tag_vocabulary_source`に`workspace_id`、対象の`note_uid`、`expected_revision`、
   一行の`reason`を渡す。初回の`expected_revision`は明示的に`null`、指定変更では現在の
   `source.revision`をそのまま渡す。候補にUIDがない旧ノートは、既存のauthority付き移行を先に行う。
4. 指定後に`tag_vocabulary`を取り直し、`source_status=pinned`と対象UID・語彙を確認する。

workspace不一致、古い版、未知引数、存在しないUID、退役・通常参照できないノートは拒否する。
指定変更はAIが判断して行い、個別の本人合意や専用GUIでの承認を要しない。内容を読んだことや
意味的に正しい選択かはコアの認証対象ではない。指定解除による制約回避の口は設けない。

| 状態 | 語彙の扱い |
| --- | --- |
| `unconfigured`・候補0件 | 現用タグを初期語彙として返す。現用タグもなければ個数・語形だけを検証し初期起票を許可 |
| `unconfigured`・候補1件以上 | 候補ID/UID/題名を返す。通常のタグ指定は正本の指定完了まで拒否 |
| `pinned` | 指定UIDの本文だけを読む。改名や似た題名の追加では正本を変更しない |
| `missing` | 指定UIDが欠損。別候補や現用語へ切り替えず、復元または版付き再指定が必要 |
| `unavailable` | 指定先が退役・通常参照不可。状態の修復または版付き再指定が必要 |

`glossary_note=null`だけをbootstrapの根拠にしない。DBやdocumentの読取失敗はエラーであり、
上表の未指定・空表へ置き換えない。通常`get`やタグを省略する本文更新は、語彙の未指定・
指定先欠損だけを理由には止めない。workspace不一致や指定JSONの破損は共通のDB準備で拒否する。
正本の欠損・未指定は、お手入れ用データでは正本の問題1件として検出し、全ノートのタグ違反へ水増ししない。
この問題の専用GUI表示は未実装である。

## 語彙を変更するとき

1. read面の`tag_vocabulary`を引数なしで呼ぶ。指定を確認し、未指定なら上の手順で先に指定する。
   `glossary_note`は指定UIDの現在のノートID、`entries`は語彙と説明、`skipped`はタグ形式が
   不正な項目、`enforce_vocabulary`は語彙制約の有無を示す。
2. そのIDを`get`で全文取得し、運用と本人の明示的な訂正を確認する。既存語で表せる場合は
   その語を使い、新しい分類が必要かをAIが判断する。
3. maintenance面の`plan_tag_vocabulary_change`へ`changes`と一行の`reason`を渡す。
   `changes`は`upsert`（タグと説明の対応表）、`remove`（削除語の配列）、
   `replace`（旧語と最終語の対応表）の3項目をすべて持たせ、使わない項目は空にする。
   理由と説明はそれぞれ1〜500文字。語彙の追加・説明変更は`upsert`、未使用語の削除は`remove`、
   改名・統合は`replace`を使う。新しい置換先は同じ要求の`upsert`で登録できる。
4. 返された件数、最大20件の例、`blockers`の集計と`can_apply`を確認する。
   `can_apply=false`なら原因を解消し、再計画する。同じ語への重複操作や置換の連鎖・循環、
   使用中の語の単純削除、保護対象の変更、タグ制約違反を迂回しない。
5. write面の`apply_tag_vocabulary_change`へ返された`receipt`を変更せず、新しいULIDの
   `execution_id`と渡す。正本UID・指定revision・原文hash・全ノートのsnapshotを再照合し、
   語彙表と全対象タグ・索引・出力待ち・履歴を一つのtransactionで保存する。
   古い計画や先行する未出力更新は拒否する。この確認は本人の承認待ちではない。
6. 保存結果と履歴を確認し、`tag_vocabulary`を再取得する。新語の追加だけでは任意のノートへ
   自動付与しないため、登録を確認してから通常の`propose`または`update`で使う。
   統合・改名の対象タグは一括適用で付け替え済みとなる。理由と結果を報告する。

planは準備済みDBの同じ読取snapshotで全対象を列挙し、DB初期化・修復・同期・書出しを行わない。
全原文をAIへ往復させず、影響件数・少数の例と計画控えだけを返す。
一回は最大1000操作、対象ノートは10万件、対象原文は256 MiBまで。上限超過時に部分適用しない。

指定した語彙表が空でも`enforce_vocabulary=true`を維持する。語彙節の重複や不正な表など、
計画できない形式は通常の`update(body)`で修復できるが、使用中の登録語を削除してはならない。
旧humanノートや保護された提案票の更新は従来どおり拒否する。

## 保存結果と履歴を確認する

`apply_tag_vocabulary_change`の`stored:true`はDB保存の成功を表す。書出しが失敗しても維持し、
`pending_exports`と警告を返す。待ち件数を確認できない場合は`null`と警告を返し、0件と推測しない。
ファイル群自体は一括の原子的置換ではない。出力待ちは変更前後の原文を照合して再開できるため、
保存済みのapplyを新しい実行IDで再送しない。応答を失った場合も、最初の実行IDで履歴を確認する。

read面の`list_tag_vocabulary_changes`は実行の要約、`get_tag_vocabulary_change`は指定した
`execution_id`の要約とノートID・UID・変更前後のタグ/hashを返す。いずれも`limit`は既定20・最大100、
返された`next_cursor`を次の`cursor`へ渡して続きを読む。履歴取得は読取り専用で同期を行わず、
原文を返さない。現在非参照になったノートのmetadataも除外する。
変更前後の原文は端末ローカルDBに保持し、Gitの論理snapshotへ履歴台帳を含めない。
fresh cloneにはノート内容と正本指定が復元されるが、過去のローカル履歴は引き継がれない。

## 指定の保存と復元

指定と出力待ちの記録は同じSQLite transactionで確定する。`.kb-tag-vocabulary.json`はGitで
追跡する復元用データで、語彙本文を複製しない。出力失敗は保存済み・未出力として返し、後続の
通常同期・書込みで再出力する。競合するファイルは黙って上書きしない。指定の再変更は前の出力完了を待つ。
指定中のノートと出力待ちの旧指定ノートは、出力側にも安全に新指定が反映されるまで削除・参照不可化を拒否する。

fresh cloneと明示importは、ノートと指定を同じtransactionで復元する。指定の欠損・不正UID・
workspace不一致を未指定に変換しない。既に指定がある保管庫で追跡ファイルだけを消して解除することも拒否する。
論理snapshotは指定を含む場合v2とし、UID・版もdigestへ含める。未指定の旧保管庫はv1と従来のdigestを
維持する。対応するアプリへ更新し、起動済みのMCPも再接続してから使用する。

## 統合・削除

AIが重複や用途を判断し、上のplan→applyで統合・改名を行う。コアは退役済み・旧human・非参照の
提案を含む全保存ノートの使用状況を数える。変更できない利用ノートが一つでもあれば全体を止め、
非参照ノートのIDや題名は例へ出さない。付け替えは順序を保ちながら重複タグを除き、1〜4個を維持する。

通常の正本本文更新・正本切替でも使用中の語の削除を拒否する。明示importでは、旧語彙と
全ノート同期後の最終状態を比べるため、ファイル順序に依存せず語彙と利用の不整合を拒否する。
通常updateの連続実行が一括処理になるわけではなく、まとまった変更には専用のplan→applyを使う。
DB確定までは全件成功または全件未反映とし、保存後は出力再開・履歴から確認する。

## 保存した変更を戻す

1. read面の`get_tag_vocabulary_change`で元の`execution_id`の内容と`rollback`を確認する。
   `rollback`があれば復元済みである。応答を失ったときも、まず同じ元実行IDの履歴を確認する。
2. maintenance面の`plan_tag_vocabulary_rollback`へ元実行の`execution_id`と一行の`reason`を渡す。
   影響件数・最大20例・blockerを確認する。判断はAIが行い、タグごとの本人確認は追加しない。
3. blockerがなければwrite面の`rollback_tag_vocabulary_change`へ、返された`receipt`を変えず、
   新しいULIDの`rollback_id`と渡す。古い計画なら再計画し、保護や競合を無視して進めない。
4. `stored:true`と出力待ちを確認し、元実行IDの履歴と`tag_vocabulary`を読み直す。
   書出し失敗時もDB復元は保存済みであるため、別のrollback IDで再送しない。

復元は、現在の対象ノートが元実行の直後と一致する場合だけ、履歴の変更前原文へ一括で戻す。
統合先のタグから元を推測せず、本文やmetadataも保存していた原文へ戻す。
一つでも対象の更新・改名・削除、保護状態への変化、正本UID/revisionの変更、出力待ちがあれば全体を止める。
対象外のノートが復元で消える語を使い始めた場合も拒否する。計画取得前の無関係な変更は許すが、
計画取得後の全DB snapshotの変化は再計画を求める。
復元前後の原文合計256 MiB・10万対象を上限とし、過去のタグが現在契約や復元後語彙に違反する場合も拒否する。

今回の復元者・理由・時刻は別台帳へ残し、元の実行と変更前後の原文は消さない。
同じ実行を戻せるのは一度だけで、復元操作そのものを再度rollbackするAPIはない。
復元には同じworkspaceの端末ローカル履歴が必要で、fresh cloneや別端末に台帳がない場合は利用できない。
専用GUIはまだなく、履歴と計画はMCPで確認する。

## 実際の運用を計測する

read面の`get_tag_vocabulary_stats`を引数なしで呼ぶ。初回の結果を基準にし、一定期間動かした後に
再取得して差分を比べる。取得だけで同期・修復・計測ログの追記は行わない。

| 項目 | 観測していること |
| --- | --- |
| `apply_runs` / `rollback_runs` | 端末ローカル履歴に保存済みの適用・復元件数。復元済みの適用も含む |
| `applied_note_changes` / `restored_note_changes` | 各実行で変更した延べノート件数。正本自身を含み、同じノートの再変更は再度数える |
| `first_recorded_at` / `last_recorded_at` | 適用と復元を合わせた最初・最後の記録時刻。履歴なしは`null` |
| `recent` | 最近10実行までのID・種別・時刻・件数。復元は`target_execution_id`に元実行IDを持つ |
| `pending_exports_total` | 現在のノート出力待ち行数。語彙以外の通常更新も含む。正本指定ファイルの出力待ちは含めない |
| `tag_vocabulary_pending_exports` | 上記のうち語彙の一括適用・復元で残っている出力待ち行数 |

`measurement_scope=local_committed_history_all_time`が示すとおり、この端末の保存済み全期間だけを集計する。
空の履歴は0件で、取得失敗は0件に置き換えない。fresh clone前の履歴や他端末の試行を含む値ではない。
`unmeasured`の計画回数・拒否試行・実行時間・意味判断品質は未計測であり、成功率や誤判断率は算出できない。
復元件数があるだけで誤判断だったとは決めず、履歴の理由と本人の訂正・調査結果を合わせて評価する。
個々の語彙を本人が一覧で確認する手順は必須にせず、AIがこの集計と根拠を使って運用を振り返る。
