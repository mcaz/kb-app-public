# ADR-0022: 語彙と利用ノートを同時に変更する

- 状態: 採用（2026-09-08、第4段階まで）
- 関連: 契約1 / ADR-0004 / ADR-0011

## 背景

語彙の正本は第2段階でworkspace IDとnote UIDへ固定した。一方、正本の表から語を消して
通常updateを順番に呼ぶだけでは、途中失敗・別クライアントの保存で語彙と利用がずれる。
数万件のノートを想定すると、AIへ変更前後の全文を送り返す方式も適さない。
本人は語彙の付与・新設・統合・削除をAI判断に委ね、個々の合意待ちを求めていない。

## 決定

maintenance面の`plan_tag_vocabulary_change`へ3種類の操作を指定する。

- `upsert`: タグ名から説明への対応表。追加と説明変更。
- `remove`: 未使用の登録語だけを削除。
- `replace`: 旧語から最終語への対応表。改名または複数語の統合。

同一語への操作重複、置換の連鎖・循環、存在しない変更元、未登録の置換先、実変更なしを拒否する。
新しい置換先は同じ要求のupsertで登録できる。理由は一行で保持する。
AIは影響件数・最大20件の例・集計されたblockerを読み、write面のapplyへreceiptを渡す。
この二段階は変更前提の照合であり、本人への承認依頼ではない。

planは同じread transactionで正本原文と全notesを読む。receiptはsource UID・指定revision・
正本document hash・全snapshot・操作・理由へ固定する。applyはBEGIN IMMEDIATEでwriterを排他し、
同じ計画を再構成して一致を確認する。指定revisionが同じでも正本本文が変われば不一致になる。
実行IDはULIDで、応答を失った場合は同じIDで履歴を取得する。二重実行と未出力の先行更新を拒否する。

コアが全persisted notesの使用状況を列挙する。廃止済み・旧human・非参照の提案も使用件数に含める。
removeに利用が残る場合、保護された対象が含まれる場合、変更後が1〜4タグ・最終語彙を満たさない場合は
全体を止める。replaceはタグの順序を保ちながら重複を除く。旧ノートのUIDやauthorityを推測して追加しない。
正本の運用本文と他の表を残し、語彙節の一つの表だけを置換する。曖昧な複数表や重複行は先に修復する。

適用は利用ノート、最後に正本を保存する。すべてのDB原文・索引・蒸留job・outbox・前後履歴を
一つのtransactionへ積む。通常の正本本文updateと指定切替にも使用語削除guardを置き、迂回を防ぐ。
importは旧語彙を取得し、全ノート同期後の最終状態へguardを掛けて入力の順序依存を避ける。

MarkdownはDB確定後のadapterであり、ファイル群そのものを原子的には置換できない。
一括操作のoutboxを一つのグループとして扱い、全before/afterを検査、ノート出力、索引生成1回、
log追記1回、Git commit1回、outbox一括消去の順に進める。途中中断してもbefore/after両方を受け付け、
同じlog markerとGit内容へ再開できる。出力失敗を未保存と報告せず、保存済みと出力待ち件数を返す。

履歴はschema12の`tag_vocabulary_runs`と`tag_vocabulary_run_notes`に分ける。前後原文はDBだけに保存し、
履歴一覧は実行の要約、詳細はhash・タグ変更metadataをページ化して返す。現在の非参照ノートは詳細から除外する。
一覧を開くたびに過去の原文全体をparseしない。通常openでは固定DDLを照合し、診断・限定復旧で
原文hashと件数の整合を検査する。派生索引の復旧で履歴を消さず、新版の欠損を空表へ再生成しない。

## 範囲と検証

最大1000語の操作、10万対象ノート、対象原文256 MiBまでを一回の上限とする。
本文を切り捨てたり、上限までを部分適用したりしない。planは数万件でも原文を応答へ含めず、
出力と履歴保存を含む1万件fixtureの明示性能テストを設ける。
stale・改ざん・二重適用、最終書込失敗、正本自身の付替え、保護対象、metadata維持、出力中断と再試行、
使用語削除の通常write/import経路、履歴と復旧境界を回帰テストで守る。

## 保存済み変更の復元（第4段階）

語の統合は多対一であり、現在のタグへ逆向きのreplaceを掛けても元の付け方には戻せない。
同じworkspaceのローカル履歴にある変更前原文を復元し、元の実行履歴は上書きしない。
AIが理由を付けて`plan_tag_vocabulary_rollback`で計画し、
`rollback_tag_vocabulary_change`へ返されたreceiptと新しいrollback IDを渡す。
復元の必要性をAIが判断し、個別承認は追加しない。

計画は元実行のID・履歴hash・現在の正本UID/revision・全DB snapshot・理由へ固定する。
元実行の変更対象すべてについて、現在原文・UID・参照可否とタグ索引が実行後の内容と一致することを
検査する。対象の更新・改名・削除、正本の再指定、保護された対象、既存の復元済み記録、出力待ちは
全体のblockerとする。履歴にないノートが復元で消える語を使っている場合も拒否し、語彙外の利用を残さない。
復元計画を取得する前の無関係なノート変更だけでは拒否しないが、計画取得後の変更は全snapshotで検知する。
最大20例・10万対象ノート・before/after原文合計256 MiBの上限を設け、原文や非参照対象の識別情報を応答へ出さない。
変更前のタグが現在の個数・語形・復元後語彙に違反する場合も拒否し、過去の不正状態は復元しない。

復元時はwriter lock下で計画を再照合し、正本を最後に、全対象の変更前原文をそのまま戻す。
tags以外の本文・authority・relations・generatedも元の原文に含まれる。今回の復元者・時刻・理由は
schema13の`tag_vocabulary_rollbacks`へ別に保存し、元のgeneratedを今回のものに書き替えない。
復元台帳、全ノート、索引、蒸留job、出力待ちは同じtransactionで確定する。
元実行IDは一意制約により一度だけ復元でき、applyとrollbackの実行ID衝突も拒否する。
Markdown/Git出力は一括applyと同じ再開可能な経路を使い、出力失敗は保存済みとして扱う。
応答喪失時は元実行IDの履歴に付く`rollback`を読み、別IDで再送しない。

復元台帳は元実行への外部キーと一意制約を持つdurable stateであり、schema13から必須とする。
既存のschema12は履歴原文を変えずに空の復元台帳を追加する。診断・限定復旧では元実行との対応と件数も
照合して保持する。schema13での台帳欠損や、古いschema宣言への新しい台帳混入は修復で隠さない。
履歴のlist/getは元実行の要約へ復元記録を添える。復元の取り消しを復元APIから繰り返す機能は設けない。
別端末やfresh cloneへ復元用台帳を運ぶ機能と専用GUIは、引き続き範囲外である。

## 実運用を測る

`get_tag_vocabulary_stats`は準備済みDBの同じread snapshotから、保存済みapply/rollbackの件数、
それぞれの延べ変更ノート件数、最初と最後の実行時刻、最近10実行、現在のノート出力待ちを返す。
集計対象はこの端末に残る全期間のローカル履歴で、復元済みapplyも適用件数から差し引かない。
ノート件数には変更された正本自身を含み、異なるノートの総数とは扱わない。
最近の実行は時刻と種別・IDで順序を固定し、原文・操作JSON・理由は読み出さない。
DB全履歴の原文parseや新しい大量ログ、同期・修復は追加しない。

計画を立てた回数、拒否された試行、実行時間、意味判断の品質はこの台帳では観測していない。
応答の`unmeasured`に明示し、保存件数を成功率・復元件数を誤判断率として提示しない。
実運用では一定期間の集計差分と履歴の理由を照合し、本人の明示訂正や調査で得られた根拠と併せて評価する。
1万件fixtureの実測は性能試験の結果として分離し、実KBの処理時間と推測しない。
