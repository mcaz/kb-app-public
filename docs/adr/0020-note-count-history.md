# ADR-0020: ノート数の実測値を端末内に日次で残す

- 日付: 2026-09-06
- 状態: 採用（記録基盤とホームの推移表示）

## 背景

ホームでノート数の推移を確認したいという本人の依頼を、PRごとに小さく実装する。
現存ノートの作成日からは削除済みノートや過去の状態変更を復元できない。
起票成功応答も保存ノート数と一致しないため、実際に確認した件数を蓄積する。

## 決定

`kb-core::note_count_history`が、アプリのバックグラウンド保守処理後に現在のDB件数を
観測する。ノートを表示する前景処理やMCPのread操作には記録処理を足さない。
復元済みのDBから総数と`status='deprecated'`の件数を同じsnapshotで数え、表示値は
既存のHomeタイルと同じ総数-deprecated数とする。statusがNULLの旧ノートも総数に含む。
未commitの変更や復元途中のDBは観測しない。
同期に失敗した場合も、端末の確定済みDBから確認できた件数を記録する。
同期先の最新状態と一致していることは保証しない。

保存先は`app_data_dir()/note-count-history/history.sqlite3`。workspace IDと観測時の
端末日付をキーにし、観測時刻（epoch milliseconds）・UTC offset・総数・deprecated数を
保持する。同日の新しい観測だけで更新し、遅れて届いた古い観測で上書きしない。
ノート本文・タイトル・ノートIDは保存しない。

日付は観測時の端末日付として固定する。旅行などでtimezoneが変わっても、過去の行を
現在のtimezoneで区切り直さない。グラフは「その日にこの端末で最後に確認できた
ノート数」を表し、日末の厳密な件数や、その日に発生したすべての変更を保証しない。
観測がなかった日・導入前の過去を0件や直前値で埋めない。空のDBを正常に確認した0件は
実測値として保存する。

## 保存範囲と障害

履歴はこの端末の観測で、Git同期・fresh cloneからの復元対象にしない。検索索引の
再構築先に含めず、`index.db`のschemaを変更しない。同じworkspaceを索引から再構築しても
端末内の履歴は保持するが、別端末や履歴ファイルの喪失から復元できるとは扱わない。

AI連携のON/OFFを計測する会話台帳とは分け、管理アプリの保守処理として件数を観測する。
記録不能は`NoteCountHistory`の劣化として返し、ノートや保守処理の成功を取り消さない。
破損・未知schema・不正な既存履歴は空の台帳へ置き換えない。
初回は一時DBの初期化が完了してから公開し、競合した別の記録を上書きしない。
既存DBではSQLiteの通常のクラッシュ回復を許容し、transaction内でschemaと履歴を
検証してから追記する。

## ホームでの表示

今日を含む直近14暦日を表示し、欠測日の前後を線でつながない。1点だけの履歴や0件も
実測として点を表示する。最新の観測値は記録日と併記し、期間合計や現在の正確な件数とは
扱わない。日別一覧で未記録と実測の0件を区別する。
タイムゾーン移動で記録日が戻る場合もあるため、最新値は日付の大小ではなく観測時刻で選ぶ。

読み取りは書込みと独立したread-onlyのsnapshotで、履歴ファイルや保存directoryを
作らない。記録なし・読取失敗を区別し、読取失敗時は古いグラフを表示し続けない。
SQLiteのクラッシュ回復が必要な場合は読取不能とし、次の保守処理で書込み側が回復する。
記録と同じくAI連携のON/OFFに依存しない。

## 判断の理由

`index.db`内のtransactionへ記録を同居させれば、各ノート変更と履歴を原子的に確定できる。
一方、今回の日次観測にはschema移行と旧バイナリの停止を伴い、履歴だけの障害が
ノートDBを開けない状態へ波及する。今回は保守処理時点の実測へ範囲を絞り、独立した
SQLiteへ記録する。ノート変更ごとの記録は必要になった段階で追加する。
