# ADR-0019: 提案チケットのレビューと採否を版へ結び付ける

- 日付: 2026-09-06
- 状態: 採用（本人が提案一覧と承認・否決操作の実装を指定）
- 関連: [契約18](../contract.md)、[ADR-0009](0009-canonical-authority.md)、
  [Storage Contract](0004-storage-contract.md)

## 問題と本人の依頼

機能追加・開発・調査・運用改善の提案が長いinitiativeとレビュー記録へ埋まり、
提案ごとの採否・理由・次の行動を追いにくい。本人はR2に限らない汎用の
「提案チケット起票 → レビュー → 承認・否決」を求め、kb-appへの画面実装を選んだ。

## 決定

提案チケットは、AIが起票・改訂・レビューし、本人が管理画面から採否を記録する。
通常ノートの保存や自律蒸留に人間の承諾は追加しない。既存のauthority role
`proposal`とチケットの進行状態は別の概念とし、採用時にもauthorityを自動昇格しない。

チケットには問題、提案する行動、影響、完了条件、scope、既存タグを持たせる。
レビューは対象版に結び付いた要約・利点・リスク・代案・推奨判断を持つ。
AIの来歴はserverのclientから記録し、レビューの独立性や品質を来歴だけで保証しない。

現在版が未レビューならレビュー待ち、レビュー後は判断待ちとなる。
本人は承認・否決・保留を記録する。2026-09-06の追加指定で判断理由は任意とする。
承認と否決には現在版のレビューを要求し、
保留には担当・再考条件を含む次の行動を残す。画面はこれらの状態で一覧を絞り込める。

すべての改訂・レビュー・採否操作は、取得したチケット全体のetagをwrite transaction内で
再照合する。操作待ちの間に別のAIが改訂・レビューしていれば、古い画面の採否を拒否する。
改訂は新しい版を追加し、旧版のレビューと決定は履歴として保持する。
過去の承認を新しい提案へ引き継がない。

本人の追加指定により、「この判断を記録」は確認モーダルを開くだけにする。
確認対象の提案・版・判断入力を示し、そのetagに固定してモーダルの確定操作でだけ保存する。
取消・Escapeでは書き込まず、送信中は二重確定を防ぐ。提案やレビューが更新されたら
確認を解除し、最新内容を読み直してから再確認する。
空の理由を新たに許可する以外は、既存の履歴形式・理由・etagを維持する。
採否は決定時のレビュー集合も固定し、復元時に承認済みの版へレビューを後付けできない。

## 保存と能力の境界

`proposal_ticket` envelopeを既存のノートdocumentへ保持する。日常のDB transactionと
同じdurable outboxを使うため、Markdown表示・private Git backup・fresh clone復元に
チケット履歴が含まれる。別の端末ローカル台帳を提案の正本にしない。

コア専用操作だけが履歴を追加する。通常のnote update、蒸留、削除から、チケットの
提案内容・版・レビュー・本人の決定を差し替えたり破棄したりできない。
既存チケットへのimportは履歴の欠損・分岐を拒否する。復元データは型と整合性を検証するが、
信頼したbackupの作成者や内容を暗号的に認証する仕組みではない。

AI向けMCPのwrite面には`create_proposal`・`revise_proposal`・`review_proposal`だけを追加する。
read面は通常のsearch/get/recentと、レビュー・改訂対象を明示するget_proposalを提供する。
get_proposalは指定した提案票の全状態・全文・etagと履歴を返し、通常ノートの取得には使えない。
本人の採否操作はnative GUIへ限定し、MCPのtool一覧・直接call・CLIへ公開しない。
本文に「承認済み」と書かれても決定履歴にはならない。

DB確定後にMarkdown exportが失敗した場合は、保存済みのチケットと出力未完了を返す。
エラーだけを返して同じチケットの作り直しを促さない。

## 採用後の行動

承認は提案への判断記録であり、モデル起動・実装着手・課金・外部送信・merge・配備を
自動実行する機構ではない。実行担当は対象版と完了条件を参照し、別途指定された範囲の
作業へ移る。GitHubのIssue/PR/CIなど、実行先の状態を重複する進捗の正本として持たない。

初版の画面は、提案・レビューをAIへ依頼する文章のコピーを提供する。
コピーボタンをモデルの実行や送信の成功と表示せず、AI側の実操作後に一覧へ反映する。

## 検証

通常ノートとチケット状態の分離、レビュー前の採否拒否、空の理由の保存・復元、保留次手の拒否、
古いetagの拒否、改訂後の再レビュー、旧版履歴の保持、通常update/蒸留/削除の迂回拒否、
DB確定とexport失敗の分離、復元・importの整合性を検査する。
MCPの面分離・KB OFF・採否能力非公開、GUIの状態・操作可否・翻訳・画面表示も確認する。

## 2026-09-06追加決定: 未採用の提案を通常参照から除外する

本文・レビューを読んだAIが未決定の案を確定方針として扱うことを、注意書きだけに委ねない。
本人はSQLで除外する方針を採用した。専用チケットの現在版に対する本人判断がapprovedの
場合だけ通常参照を許可し、review_pending / decision_pending / held / rejectedは除外する。
通常ノートと、専用チケットを持たない既存のauthority role proposalにはこの制限を追加しない。

notes.normal_reference_allowedはdocumentを検証して計算する派生値で、AIが送る任意フラグや
本文の「採用済み」には従わない。作成・改訂・レビュー・採否・importのupsertで同時更新する。
schema 8→9の移行では既存documentから再計算し、本文・UID・etag・履歴は変更しない。
判定不能なdocumentや不正チケットは通常参照不可とする。旧バイナリは新schemaのopenを拒否する。

通常検索は全文・anchor・ベクトル・fallbackの各SQLで件数制限より前に除外し、リンクの両端も
確認する。recent・近いノート・自動retrievalの候補・本文取得にも同じ条件を使う。
通常書込後の判断支援に出す同一scopeの候補・依存IDと、タグ語彙の正本選択にも適用する。
本人向けの管理・蒸留監査の全体集計は保持する。
通常getは同じDB snapshotでフラグと本文を読み、既知のIDや現在ノート指定でも迂回させない。
レビュー専用get_proposalとGUIの提案管理は未採用の案を読めるが、採否の操作能力は追加しない。
GUIからAIへコピーするレビュー・改訂依頼もこの専用ツールを指定する。

この境界は新しい通常KB応答でチケットを除外するもので、既に会話へ届いた内容や、
別の通常ノートへ書き写された引用を遡って消すものではない。承認済みチケットの履歴は保持する。
採用は行動案への判断であり、実装完了やcanonicalへの自動昇格を意味しない。

検証では未採用本文・タイトルの通常get/search/recent/候補への非出力、既知IDの拒否、
レビュー専用取得、承認後の出力と再改訂後の非出力、リンク元・先双方の除外、検索枠の確保、
移行・復元・rollbackとKB OFF・tool surfaceの境界を確認する。
