# 出典付きの判断・行動記録

2026-09-08採用。評価方法は[判断材料の運用評価](judgment-evaluation.md)を参照。

既に読み込んだ取り決めが行動選択に使われなかった問題に対し、検索順位とは別に、
読み込み後に参照できる優先理由と適用条件を渡す。ユーザーの方針を文章として繰り返すだけでなく、
記録の種類・出典・現行性・参照関係・重複をコアで処理する。

## 保存

ノートの任意フィールド`judgment`は、SQLiteの正本document、Markdown outbox、Gitバックアップに
含まれる。追加の保存先や個人MDは使わない。既存ノートへ一括付与せず、出典を確認できた記録から
通常のMCP `propose` / `update`で保存する。本文は引き続き自己完結させる。

| 種類     | 記録する内容                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------- |
| decision | 本人決定・本人訂正・AI推測の区別、出典referenceと抜粋、適用条件、選ぶ行動、例外                   |
| action   | 状況、参照した決定UID、実際の行動、成功・失敗・不明、実測・本人報告・AI報告の区別、出典、本人訂正 |

出典の区分は呼び出したAIによる申告であり、アプリが本人を認証した証拠ではない。
同じ元発言・イベントを再要約したときも`source.reference`を変えない。独立した複数の
行動の実測と、一件の行動を複製した記録を分けるためである。

decisionはrecordsのrecord、またはdecisions/proceduresのcanonicalに置ける。
actionはrecordsのrecordに置く。失効後も当時の判断を残せるよう、metadataは保持できる。
actionの`decision_refs`には同じUIDへの`supports`または`mentions` relationを要求し、
既存の参照先検証と削除保護を使う。`supports`は実際に根拠を支持する場合に限り、単に
参照しただけの行動や失敗には`mentions`を使える。

`update`で`judgment`を省略すると保持し、オブジェクトを渡すと全置換、`null`は削除する。
入力は型、空白だけの文字列、文字数、重複参照を保存前に検査する。不正なmetadataと同時に
本文を送っても、本文だけを保存することはない。未知の種類を推測して読み替えない。

## 読み込み

`get`と`search(include_documents=true)`は、同じDB snapshotから`judgment_context`を返す。
検索候補とその決定・変更関係を上限付きで辿り、各項目に元ノートのID/UID、出典、条件、例外、
優先理由、未解決事項を付ける。本文と構造化した要約は同じ保存内容に由来する。

優先度は説明できる分類であり、一つの重要度の点数にはしない。現行の明示的な本人決定、
正本との照合が必要な本人決定の記録、AI推測、行動観測を区別する。本人の訂正があれば
注意を促すが、その存在だけで旧決定を撤回しない。後継は既存のstatusとtyped relationで扱う。

`context_scope`は呼び出し側が今回の作業で確認できた場合だけ指定する。
記録のscopeと同じ、または記録のscopeの子範囲（slash境界）なら範囲一致とする。
`demo/deploy`は`demo/deploy/macos`を含み、`demo/deploy-other`は含まない。
省略時は`unchecked`、異なる場合は`outside`とし、検索ヒットだけから適用を断定しない。
一致しても自然文の条件・例外の充足は未判定である。

同じ出典イベントは一度だけ実績として数える。同一出典から異なる結果が報告された場合は
食い違いとして示す。成功回数やAI行動の反復は本人決定の優先度を上げない。
訂正記録と矛盾する正本を見つけても、自動で勝者を決めず照合が必要なことを返す。

## 配信の境界

判断要約の項目数・総量を制限する。hookでは劣化通知を優先したうえで本文より前に判断材料を
選び、条件・例外・出典を含む項目単位で採用する。途中で切って意味を変えず、入らない項目と
探索範囲の省略を件数で示す。全stdout予算には前置き・統計・判断材料・本文・候補案内を含める。

KB OFF、非公開の提案票、本文を出さない検索では判断本文も出さない。CardLite profileへ新しい
判断要約を追加しない。観測台帳は出力件数だけを保持し、判断や行動の本文を複製しない。

これは読み手の行動を決定する認可機構ではない。一般的な依頼から過去の方針撤回を推定せず、
本人の明示的な今回の変更、引用や過去ログの区別、適用条件の判断は読み手に残る。
モデル内部の重みを操作したり、確実な遵守・効果を保証したりするものではない。

## 検証

保存の互換性、MCPの入力/更新/取得、重複、現行性、scope境界、矛盾、本文とhookの予算は
決定的なテストで確認する。モデルの行動選択は[別の合成評価](judgment-evaluation.md)で測る。
原文だけの場合と、同じ原文に本番生成の判断材料を付けた場合を同じ条件で比較し、
コマンド提示・AI実行・説明・判断保留など実際に選んだ選択肢を採点する。
この選択評価も、外部アプリへの副作用を実行した受入試験とは区別する。

2026-09-08のローカル検証では、フロント211テスト、コア750テスト、アプリ側77テスト、
CLI側15テスト、fmtとworkspace全体のClippyが成功した。既存private gateの4テストは
許可付き再実行でもローカルポート作成が拒否され、未確認として残した。
判断出力の件数型を調整した後、hook出力20テストと観測台帳37テストを再確認した。
既存のrelease用1万ノート性能gateも成功し、リンク展開と判断contextを含む20回の取得は
合計7ms（予算2,000ms）だった。このfixtureにはjudgment metadataの大量投入は含まれず、
40件の行動記録で決定が要約予算から押し出されないことは別の境界テストで確認した。
