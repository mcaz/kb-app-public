# PoC: 日本語 FTS「2文字語の空振り」対策の方式比較

- 実施日: 2026-08-09
- 判定条件: 既存実装(trigram トークナイザ)が踏んだ「CJK 2文字語のクエリが構造的に
  ヒットしない」欠陥を殺せる方式を確定できるか
- **判定: 可(確定)**。A'(LIKE)と B(lindera 分かち書き)のどちらでも 2文字語の
  再現率は 0 → 1.000 になる。ただし両者は逆側に穴があるため、推奨は組み合わせ(後述)

## 比較した3方式

| 方式 | 索引 | 検索 |
|---|---|---|
| A | FTS5 `tokenize='trigram'` に原文 | `MATCH "<語>"`(既存実装相当) |
| A' | A と同一テーブル | `body LIKE '%<語>%'` |
| B | lindera(IPADIC)で分かち書き → FTS5 `tokenize='unicode61'` | クエリも同じ分かち書きを通して `MATCH` |

コーパス: 合成日本語ノート 5,000 件(各 2〜5 文、技術ノート風、計 1.0 MB)。
ターゲット語は既知の件数だけ文単位で埋め込み、生成後に部分文字列スキャンで
正解集合と完全一致することを assert 済み(偶然の出現ゼロ)。
レイテンシはウォームアップ 5 回後、31 回実行の中央値。

## 構築コスト

| 方式 | 構築時間 | DB サイズ | 備考 |
|---|--:|--:|---|
| A/A' trigram | 26.8 ms | 2,117,632 B(原文の約 2.1 倍) | 原文を索引・格納 |
| B lindera+unicode61 | 88.4 ms(分かち書き 61.3 + 挿入 27.1) | 1,794,048 B | 分かち書きテキストを格納 |

lindera の分かち書きスループットは約 16 MB/min(5,000 件 / 1.0 MB を 61 ms)。
辞書ロード(embedded)は初回 30 ms。構築コストはどの方式も実用上無視できる。

## 観測された挙動(重要)

1. **A の 2文字語空振りを実測で再現**。trigram トークナイザは 3 文字未満の
   クエリからトークンを生成せず、単独ではヒット 0(SQLite 公式ドキュメントも
   「3 文字未満の部分文字列は full-text query では一切マッチしない」と明記)。
2. **A はもっと悪質な壊れ方もする**: `運用 バックアップ` のような混在クエリでは、
   2文字語のフレーズが**黙って無視され**、`バックアップ` 単独と同じ 180 件
   (誤ヒット 169 件)が返る。0 件なら気づけるが、こちらは「それらしい結果」が
   返るため気づけない。既存実装の「語が黙って消える」と同型の故障。
   (観測: 全フレーズが空 → 0 件、空フレーズと非空フレーズの混在 → 空側だけ無視)
3. **A'(LIKE)は全クラス再現率 1.000**。trigram テーブルは 3 文字以上の LIKE を
   インデックスで最適化(0.07〜0.12 ms)し、3 文字未満はテーブルフルスキャンに
   フォールバック(5,000 件で約 1.1 ms、規模に線形 → 10 万ノートで ~20 ms 推定)。
   注意: indexed LIKE は trigram トークナイザに `remove_diacritics` を
   付けない・`case_sensitive=1` にしない場合のみ。
4. **B は全ターゲット語で再現率 1.000、レイテンシ最速**(0.01〜0.03 ms)。
   bm25 ランキングが語単位で正しく効くのも B だけ。
5. **B の構造的な穴は部分語**: `ライフサイクル` は IPADIC で 1 トークンのため
   `サイクル` では 0 件(`アップ` → `バックアップ` も同様)。形態素境界と
   一致しないクエリは構造的に落ちる。trigram/LIKE とちょうど逆側の穴。

## lindera 5.x の注意点(ハマった点)

- **v5 で API 再編**。公式サイトの quickstart は `lindera_analysis::tokenizer::Tokenizer`
  (別 crate)を参照しているが、分かち書き目的なら `lindera` 単体の
  `Segmenter::new(Mode::Normal, dict, None)` + `segment(Cow<str>) -> Vec<Token>`
  (`token.surface: Cow<str>`)で足りる。crate root に tokenizer モジュールは無い。
- **feature 名は `embed-ipadic`**(× `ipadic` × `embedded-ipadic`)。辞書ロードは
  `load_dictionary("embedded://ipadic")`。ファイル配置なら `file://<path>`
  (default feature `mmap` で mmap ロード可)→ バイナリ肥大を避ける選択肢。
- **辞書の実サイズ ≈ 55 MB(非圧縮)**。embed するとバイナリが 61 MB。
  Tauri 配布では辞書をリソース同梱 + `file://` ロードにするか、embed で単純化するかの
  トレードオフ。ビルド時に辞書を取得するためオフラインのクリーンビルドは失敗しうる
  (CI はキャッシュ必須)。
- **複合語の分割は良い方向にも働く**: `埋め込みベクトル` → `埋め込み / ベクトル` と
  割れるため `埋め込み` 単独クエリでヒットする。一方でカタカナ複合語が 1 トークンに
  なるケース(ライフサイクル)は部分語を殺す。分割粒度は辞書依存
  (UniDic は短単位でより細かい。NEologd は新語に強いが更新停止気味)。
- 分かち書きテキストを FTS に格納するため、snippet/highlight は分かち書き文面に
  かかる(空白入り)。原文表示には元テキストの別持ちが必要(実装は外部コンテンツ
  FTS5 で原文テーブル参照にすれば二重持ちを避けられる)。

## kb-app 本実装への推奨

**推奨: B(lindera 分かち書き + unicode61)を主索引、trigram 索引を併設し
LIKE / trigram-MATCH をレスキュー経路にする二本立て。**

理由:

1. 判定条件である「2文字語の空振り」は A'・B どちらでも殺せるが、
   **どちらか単独では別の穴が残る**(A' はランキング不能+2字語がフルスキャン、
   B は部分語が 0 件)。二本立てで互いの穴を塞ぐのが唯一の全勝構成。
2. B は全語クラスで最速・bm25 が正しく効く・語境界を知っているため誤ヒットも
   最少。ハイブリッド検索(FR-C3: 全文+ベクトル+リンク近傍)の FTS 側リストの
   品質は B が最も高い。
3. trigram 併設のコストは小さい(構築 27 ms / 5,000 件、DB +2.1 MB/コーパス 1 MB)。
   レスキュー経路は「B が 0 件または低ヒットのとき LIKE(全長対応・正しさ保証)/
   3 文字以上なら trigram MATCH(高速)」で足りる。
4. 辞書 55 MB はローカルデスクトップ製品(Tauri)では一回きりの固定費。
   非エンジニア向けに追加セットアップなしで日本語検索が正しく動く価値の方が大きい。

最小構成で始めるなら(段階案): まず **trigram + 「3 文字未満の語は LIKE 補助述語で
AND」** のハイブリッドだけでも欠陥自体は殺せる(依存追加ゼロ)。ただし 2字語が
ランキングに寄与しない・フルスキャンが規模に線形で伸びる制約が残るため、
本命は上記の二本立て。

## 再現手順

```
cd poc/ja-tokenize
~/.cargo/bin/cargo run --release
```

コーパスは xorshift64 の固定シードで決定的。`trigram.db` / `lindera.db` を
crate ディレクトリに生成する(.gitignore 済み)。
