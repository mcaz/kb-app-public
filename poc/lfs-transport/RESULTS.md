# PoC 結果: LFS 転送(lfs-transport)

実施日: **未実施** / 実行: `./run.sh` または `./run.sh --remote <git-url>`

## 判定: **未実施**

ADR-0003 は full 転送に同一 origin の Git LFS を採ると決めたうえで、
**実測で倒れたら第2リポジトリ方式へ切り替える**という乗り換え条件を3本付けている。
この PoC はその判定材料を採るためのもので、**結果が出るまで転送層の実装に入らない**。

| # | 検証項目 | 判定 | 実測メモ | 必要なもの |
|---|---|---|---|---|
| 1 | `content_hash` が LFS の OID と一致する | 未実施 | | git-lfs |
| 2 | 保管庫に入るのは印(pointer)だけ | 未実施 | | git-lfs |
| 3 | 実体の置き場を保管庫の外へ移せる(`lfs.storage`) | 未実施 | | git-lfs |
| 4 | 既存の GitHub 認証を対話なしで使える | 未実施 | | git-lfs + remote |
| 5 | **手で普通に clone したとき実体が落ちてこない** | 未実施 | | git-lfs + remote |
| 6 | 必要な実体だけ後から取れて、照合が一致する | 未実施 | | git-lfs + remote |

## なぜ項目1が最初に来るか

ADR-0003 決定2 は `content_hash` を raw bytes の SHA-256 に固定し、その根拠を
**「LFS の OID と一致するので、転送側と CAS 側で検証が二重にならない」**に置いている。
ここが崩れると決定の根拠ごと崩れるので、ネットワーク不要のこの項目を最初に測る。

## なぜ項目5が本丸か

レビューで **LFS 案の最大の弱点**と特定された点。ユーザーが素の `git clone` をしたときに
実体まで落ちてくるなら、「保管庫の外に置く」という決定の効果が薄れる。
対策は `.lfsconfig` の除外・アプリ側の skip-smudge・明示 fetch の3層だが、
**tracked な `.lfsconfig` が fresh clone に効くかどうか**は実測でしか分からない。

## 実行に要るもの

1. **git-lfs のインストール**(`brew install git-lfs`)。
   製品では同梱する方針だが、この PoC は素の挙動を測るのが目的なので通常の導入でよい
2. 項目4〜6 は **空の GitHub リポジトリを1つ**。
   実行すると LFS の保管容量と通信量を消費する(GitHub Free/Pro は保管 10GiB・通信 10GiB/月)。
   使い捨てのリポジトリを推奨

## 判定後にやること

- 全 PASS → 転送層の実装へ進む(ADR-0003 実装順 4)
- 項目5 が FAIL → **ADR-0003 決定2 を撤回**し、「第2リポジトリ + chunk CAS +
  blobless partial clone」へ切り替える。決定ノートと ADR の両方を更新する
- 項目4 が FAIL → 同梱の認証まわりを詰めるか、同じく乗り換え
