# PoC 結果: LFS 転送(lfs-transport)

実施日: 2026-08-13(項目1〜4)/ 実行: `./run.sh`
環境: git 2.53.0 / git-lfs 3.7.1 (darwin arm64)

## 判定: ネットワーク不要の4項目は **PASS(4/4)**。remote が要る3項目は**未実施**

ADR-0003 は full 転送に同一 origin の Git LFS を採ると決めたうえで、
**実測で倒れたら第2リポジトリ方式へ切り替える**という乗り換え条件を3本付けている。
この PoC はその判定材料。**残る3項目が出るまで転送層の実装には入らない。**

| # | 検証項目 | 判定 | 実測 |
|---|---|---|---|
| 1 | `content_hash` が LFS の OID と一致する | **PASS** | 3MB のランダムデータで `shasum -a 256` と pointer の `oid sha256:` が一致 |
| 2 | 保管庫に入るのは印(pointer)だけ | **PASS** | pointer は **132 バイト** |
| 3 | 実体の置き場を保管庫の外へ移せる(`lfs.storage`) | **PASS** | 外 1 件 / `.git/lfs` 0 件。`LocalMediaDir` が sidecar を指す |
| 4 | 後から設定しても既存の実体は移らない(順序の罠) | **PASS**(想定どおり) | 実体を作った後に `lfs.storage` を張っても `.git/lfs` に残る |
| 5 | 既存の GitHub 認証を対話なしで使える | 未実施 | remote が要る |
| 6 | **手で普通に clone したとき実体が落ちてこない** | 未実施 | remote が要る |
| 7 | 必要な実体だけ後から取れて、照合が一致する | 未実施 | remote が要る |

## 項目1 が通った意味

ADR-0003 決定2 は `content_hash` を raw bytes の SHA-256 に固定し、その根拠を
**「LFS の OID と一致するので、転送側と CAS 側で検証が二重にならない」**に置いていた。
この前提は**実測で成り立った**。`kb-core` の `ContentHash`(SHA-256)をそのまま
LFS の OID として扱ってよい。

## ハマった点(実装に効く)

1. **`lfs.storage` は「最初の実体を作る前」に張らないと効かない。**
   最初の測定は FAIL したが、原因は LFS ではなく測る側の順序ミスだった
   (`git add` で実体が `.git/lfs` へ書かれた**後**に設定していた)。
   張り直しても既にある実体は移らない(項目4)。

   → **製品では「保管庫を作った直後・clone した直後」に張る必要がある。**
   `connect.rs` の `ensure_merge_config` が clone した側でも毎回冪等に
   merge 属性を張り直しているのと同じ場所・同じ理由で、`lfs.storage` も張る。
   遅延して張ると、それまでに取り込んだ実体が保管庫の中に取り残される。

2. pointer は 132 バイト。「保管庫に入るのは印だけ」という決定2 の文言は
   実測でも妥当(3MB の実体に対して 0.004%)。

## 残る3項目に要るもの

空の GitHub リポジトリ1つ。実行すると LFS の保管容量と通信量を消費する
(GitHub Free/Pro は保管 10GiB・通信 10GiB/月)。使い捨てを推奨。

```bash
./run.sh --remote git@github.com:<owner>/<scratch>.git
```

**項目6 が本丸。** レビューで LFS 案の最大の弱点と特定された点で、
tracked な `.lfsconfig` の除外が fresh clone に効くかは実測でしか分からない。

- 項目5 が FAIL → 同梱の認証まわりを詰めるか、同じく乗り換え
